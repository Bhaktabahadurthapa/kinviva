# Interview Practice

Interview Practice helps you rehearse Cloud/DevOps, system design, AI engineering and coding questions. It sits in the **Interview** tab and uses the AI provider you already set up in Settings → AI. There is no new configuration and no extra provider.

## Modes

**Explain answer.** Pick a category, type or paste a question (or press "Use the latest question from the meeting" to copy the newest question heard from the other side), and press **Explain answer**. The result has four parts:

- **Say it**: a short answer you can say aloud (about 30 seconds).
- **Understand it**: the technical explanation with an example. For coding, the code appears here in the language you chose.
- **Tradeoffs and assumptions**: each line is marked Tradeoff, Assumption or Uncertain.
- **Likely follow-up question**.

**Practice first.** You see no coaching until you write your own answer and press **Check my answer**. The feedback covers correctness, missing points, structure and clarity, plus a stronger spoken version and a likely follow-up. Any score is labelled *coaching feedback, not a calibrated hiring assessment*. You can then press **Show the model answer**.

The coding category adds an **Answer language** choice (Python, Java, C++). The application itself stays Rust and TypeScript.

Nothing is sent to the AI until you press the button, so partial transcript updates never trigger calls. Pressing the same request again while it is running reuses the running call.

## How a request is built

Each request has four separate parts:

1. Application rules (system message): honesty rules, no invented experience, untrusted-data rule.
2. Skill instructions (system message): the one bundled skill for the category. Other skills are not included.
3. Output format (system message): the JSON shape for the mode.
4. Data (user message): your question, your draft answer, your live notes, and excerpts from your active documents, each in its own tag. The text is marked untrusted, and any text that looks like one of these tags is defused so it cannot close a block early.

## Skills

Skills live in `src-tauri/skills/<name>/SKILL.md` and use the Agent Skills layout from [anthropics/skills](https://github.com/anthropics/skills): YAML frontmatter with `name` and `description`, then Markdown instructions.

| Category | Skill |
| --- | --- |
| Cloud / DevOps | `cloud-devops-interview` |
| System design | `system-design-interview` |
| AI engineering | `ai-engineering-interview` |
| Coding | `coding-interview` |

**Edit a skill.** Change the text in its `SKILL.md`, then rebuild the app (`npm run tauri dev` or `scripts/build-mac-app.sh`). Skills are compiled into the app, so editing needs a rebuild.

**Add a skill.** (1) Create `src-tauri/skills/<new-name>/SKILL.md` with `name` equal to the folder name. (2) Add a variant to `Category` and an entry to `ALLOWLIST` in `src-tauri/src/skills.rs`. (3) Add the category to `CATEGORIES` in `src/views/InterviewView.tsx` and to `InterviewCategory` in `src/lib/types.ts`. (4) Run the tests. The loader rejects a skill whose frontmatter is missing or malformed, whose name does not match the allowlist, or whose body is under 200 or over 12,000 characters.

**What the loader will not do.** It accepts no file paths from the UI, fetches nothing from the network, runs no scripts and loads only the selected skill. Parsed skills are cached for the life of the app.

## Provider behaviour

- Reuses the same streaming client, stored API key and cancellation as the rest of the app.
- Asks for a JSON object (`response_format`). If a provider rejects that option, the request is retried without it.
- The reply is validated. If a provider cannot produce the structure, you get its plain text with a note.
- Missing key, rejected key, rate limits and network errors are shown as messages. **Cancel**, and changing the question, category, language, mode or your answer, cancel the running request. A late reply to an old request is dropped.
- Interview results are not saved to meeting history.

## Tests

Mocked (no model is called): skill loading and validation, category mapping, skill selection in requests, separation of instructions and data (including injected closing tags), response parsing and malformed output, provider outcomes, duplicate and stale request handling (Rust `skills` and `interview` tests, `src/lib/interview.test.ts`), and the JSON-option retry against a local fake server (`llm` tests).

Not covered by automated tests: live model behaviour. The skills and prompts have not been checked against a real model; answer quality, JSON compliance and speed depend on the provider and model you choose. To check, add your key in Settings, open Interview, and try one question per category.

```bash
cd src-tauri && cargo test --lib
npm test
```

## Known limitations

- Answers are generated by a model and may be wrong. They are not verified, and no code is run.
- The skills have not been tuned against a live model yet.
- Structured output depends on the provider; weaker models may fall back to plain text.
- Answers appear when complete (no word-by-word streaming) because the JSON is validated first.
- No use of a vector database: reference context comes from the existing keyword search over your active documents.
- Skills are bundled at build time; there is no in-app skill editor.
- The score is a rough practice signal, not a hiring assessment.
- Answer language applies to code only; spoken text is English.
