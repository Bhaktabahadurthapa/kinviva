# Open-core plan

Goal: a useful free **Community Edition**, and later **Pro** and **Business** editions that add value without taking away anything
people already have. Inspired by how PostHog and GitLab separate a free core from paid additions.

Status: planning only. Today there is one product (the Community Edition). Nothing in Pro or Business exists.

## Principles

1. **Nothing that ships today moves behind a paywall.** Every feature in `FEATURE_AUDIT.md` stays in Community. Paid editions add new things only.
2. **Local-first stays true.** Community works fully offline with a local speech engine and a local or bring-your-own-key answer engine. No account is needed.
3. **Honest labels.** Planned features are called planned everywhere (website, README, app). No feature is shown in the app before it works.
4. **Small, stable seams.** Paid code plugs into a few documented interfaces. It does not fork the app.

## Editions

### Community (exists today)
Local transcription; local AI and bring-your-own API key; meeting explanations, summaries and history; interview and classroom
support (basic); technical troubleshooting and diagrams (basic); Notes, Whiteboard, Visuals, Presentation maker, Discover, Video Assist, overlay.

### Pro (planned, not built)
- Agent-driven technical investigations (plans, evidence gathering, reports; any command still needs the user's approval and runs on the user's machine).
- Advanced diagram generation and reports.
- Enhanced interview and learning workflows.
- Optional managed AI service and automation (the user can still bring their own key).

### Business (planned, not built)
- Organization accounts and centralized administration.
- Shared workflows.
- Usage management and security policies.

## Where the line is drawn

| Rule | Reason |
|---|---|
| Free: anything that runs on the user's machine with the user's own models and keys. | This is the promise of the product. |
| Paid: hosted services (managed AI, sync, accounts), team features, and new advanced workflows. | These cost money to run or only matter to teams. |
| Never paid: privacy controls, data export, deleting your data, reading your own history. | Trust. |

## Code structure

```

  src/, src-tauri/            app (React, Tauri, Rust, SQLite), unchanged
  src-tauri/src/edition.rs    edition and feature registry (added in this change)
  cloud/early-access/         early-access signup service (code only, not deployed)
kinviva-pro/                  private repository (to be created): Pro modules
kinviva-cloud/                private repository (to be created): accounts, licensing, managed AI
kinviva-site/                 public marketing site (today: the `site/` folder generated by scripts/gen-site.py)
```

### Stable feature interfaces (the seams)
The app already separates features cleanly enough that these four seams are enough. Each is a small Rust trait or a typed Tauri command, versioned, with a Community default.

1. **Edition and entitlement**: `edition.rs` answers "which edition is this and is feature X available". Community returns the free set. A Pro build returns more. No feature checks anything else.
2. **Investigation provider** (for the planned agent investigations): `plan(symptom) -> steps`, `propose_command(step) -> command`, `record_evidence(...)`. Community has the existing read-only troubleshooting as the default provider. The app, not the provider, decides whether a command may be shown.
3. **Report and diagram renderers**: `render(model, template) -> file`. Community has the Mermaid diagram and Markdown export. Pro can register more templates.
4. **AI gateway**: `chat(request) -> stream`. Community talks to the user's endpoint. A managed gateway is one more endpoint, so managed AI needs no change in the app beyond a sign-in.

Pro modules are built as a separate crate or npm package that the private repository adds at build time. The public app never imports private code.

## Phasing

| Phase | What | Gate |
|---|---|---|
| 0 (this change) | Plan, audit, edition registry, early-access form, CI | Local only, nothing published |
| 1 | Decide the Community license (see LICENSING_REVIEW.md); clean up flagged documents | Owner decision and legal review |
| 2 | Signed and notarized macOS release, Windows hardware testing, safe updates | RELEASE_READINESS.md checklist |
| 3 | Early-access service deployed and the list used to choose pilot users | Owner approval to deploy |
| 4 | First Pro module (the most-requested one from the early-access answers) | Pilot demand, a private repo, a licensing design |
| 5 | Accounts and Business features | Real customer need |

## What not to do
No rewrite, no microservices before there is a hosted feature to serve, no prices on the website before the first paid feature exists, no license change without owner and legal sign-off.
